The other PCIe endpoints on this machine

The GPU is not alone on the root complex. From lspci -tv, the guest sees four separate host bridges — the GPU has its own, so GPU traffic does not contend with storage or network traffic at a shared switch:

0000:30 → 31:00.0NVIDIA AD104GL [L4] — our device
0000:2c → 2f:00.0Amazon NVMe SSD controller (root volume)
0000:24 → 27,28:00.02× Amazon ENA (Elastic Network Adapter)
0000:01 → 02–23large empty bridge fan-out (hot-plug slots)
Virtualisation caveat. This is a KVM guest (Hypervisor vendor: KVM). The PCIe topology above is the guest's view: the GPU is passed through with device assignment, so the DMA path is real silicon, but bridge numbering is synthesised by the hypervisor and the physical slot wiring is invisible. The ×8 link width against a ×16-capable endpoint is a property of the host slot, not of the L4 card.

The three host memory states

1 · PAGEABLE malloc / new
Ordinary virtual memory. The kernel may relocate or reclaim the physical page at any time, so the GPU's DMA engine cannot be pointed at it.
what actually happens
cudaMemcpy from pageable memory stages through a driver-owned pinned bounce buffer: CPU copies into the staging buffer, then the DMA engine copies out. Two passes over the data, and the copy is synchronous-ish. Typically caps out near ~6–9 GB/s on this link — well under the ~13–14 GB/s the link can do.
2 · PINNED / PAGE-LOCKED cudaHostAlloc, cudaMallocHost
Page-locked, so the physical address is stable and registered with the IOMMU. The GPU copy engine DMAs directly, no bounce buffer, and the transfer is genuinely asynchronous — it can overlap with kernel execution on a different stream.
the only way to saturate the link
Reaches ~13–14 GB/s. Cost: pinned pages are unavailable to the rest of the system, so over-pinning starves the page cache. hostRegisterSupported = 1 PROBED — existing allocations can be pinned in place with cudaHostRegister.
3 · MANAGED / UNIFIED cudaMallocManaged
One virtual address valid on both sides. unifiedAddressing = 1, managedMemory = 1, concurrentManagedAccess = 1 PROBED.
migration, not coherence
On this machine pageableMemoryAccessUsesHostPageTables = 0 and hostNativeAtomicSupported = 0. There is no cache-coherent CPU↔GPU link here. Unified memory is implemented by GPU page faulting + page migration over PCIe, driven by the UVM kernel module. A fault-and-migrate round trip costs microseconds, so a pointer-chasing kernel over managed memory can be orders of magnitude slower than the same data prefetched with cudaMemPrefetchAsync.
Practical rule this hardware enforces. Pinned + async + streams is not a micro-optimisation on this box, it is the difference between 6 GB/s and 14 GB/s — and with 2 copy engines (asyncEngineCount = 2) you can have an H2D copy, a kernel, and a D2H copy all in flight at once.

§4 The PCIe link — lanes, BARs, doorbells, and how work actually reaches the GPU −

This is the part most diagrams draw as a single arrow. It is really a packet-switched network, three memory-mapped apertures, and a ring buffer.

The 128 B payload is a real tax. Each TLP carries a 12–16 B header for 128 B of data → ~11% protocol overhead floor, before ACK/NAK and flow-control credits. That is why measured pinned-memory bandwidth lands near 13–14 GB/s rather than 15.75. Had the platform negotiated 256 B payload the overhead would roughly halve.

The asymmetry to internalise: the CPU never pushes your kernel across PCIe. It writes commands into a buffer and rings a doorbell; the GPU then pulls. This is why launch latency (~3–10 µs) is dominated by round trips and doorbell/fence ordering, not by bandwidth — and why launching thousands of tiny kernels is fatal while launching one big kernel is free.

The ridge point. 30.3 TFLOPS ÷ 300 GB/s = 101 FLOP per byte. A kernel must do ~101 single-precision operations per byte it reads from DRAM to be compute-bound on this GPU. Almost nothing naive clears that bar — which is why §8's 70 MB of on-chip SRAM, not the FP32 count, is the thing to design around.

§9 Sub-partition datapath — one instruction's journey −

The warp scheduler is the beating heart of the machine. Every stall metric in Nsight Compute describes a warp failing one of the checks below.
1 · FETCH
Warp's program counter indexes the L0 instruction cache. Miss → SM's L1 I-cache → L2 → VRAM. A cold or thrashing instruction footprint shows as no_instruction stalls; this is why very large unrolled loops can slow down.
↓
2 · SCHEDULE — the eligibility test, every clock

The scheduler holds 12 warp slots. Each clock it examines all 12 and picks one eligible warp. A warp is ineligible if any of these hold:

Scoreboard dependencywaiting on a register a prior long-latency instruction will write → stall_long_sb / stall_short_sb
Barrierparked at __syncthreads() until all warps of the block arrive → stall_barrier
Pipe busythe functional unit it needs is occupied → stall_math_pipe_throttle, stall_mio_throttle
Memory throttleLSU queue full → stall_lg_throttle, stall_drain
Instruction not fetchedL0 miss in flight → stall_no_instruction
Branch resolvewaiting on a divergent branch's convergence barrier → stall_branch_resolving
This is latency hiding, physically. There is no out-of-order execution and no branch speculation in an SM. The only mechanism for covering a 500-cycle DRAM latency is having another eligible warp to issue instead. 12 warps per scheduler is your entire budget — occupancy is not a vanity metric, it is the size of the latency-hiding window.
↓ one warp selected
3 · DISPATCH & OPERAND COLLECT
The dispatch unit issues the instruction for all 32 lanes. Operands are read from the 64 KB register file (or the uniform register file if the value is warp-invariant — Turing+ added a scalar datapath so loop counters and base addresses don't burn vector register bandwidth). Active-mask from the convergence barrier unit determines which lanes participate; inactive lanes consume the slot and produce nothing. That is what divergence costs.
↓ routed by opcode
4 · EXECUTE — which pipe, and at what rate
PipeWidthClocks per warpInstructions

↓ memory instructions only
5 · MEMORY PATH
Coalescer32 lane addresses → minimum set of 32 B sectors. A perfectly coalesced 4-byte-per-thread warp load = 128 B = 4 sectors. Worst case (32 scattered addresses) = 32 sectors = 8× the traffic.
Shared memory bank checkAddress ÷ 4 mod 32 = bank. Conflicts serialise into extra cycles; broadcast (all lanes same address) is free.
L1 tag lookupHit → data returns in ~33–38 cycles. Miss → sector request to L2.
µTLB translationIn parallel: virtual → physical (§11). TLB miss adds a page-table walk on top of everything.
L2 via crossbarHit ~250–350 cycles. Global atomics resolve here.
GDDR6Miss → ~450–600 cycles, and the DRAM row/bank state decides where in that range you land.
↓
6 · WRITEBACK
Result written to the register file; scoreboard bit cleared, which is what makes any warp waiting on that register eligible again. In-order retirement per warp — no reorder buffer anywhere in the SM.

The critical negative result on this machine. pageableMemoryAccessUsesHostPageTables = 0 and hostNativeAtomicSupported = 0 PROBED. That means:
  • The GPU does not walk the host's page tables. There is no ATS/PRI or HMM-coherent path.
  • There is no cache-coherent CPU↔GPU interconnect (no NVLink-C2C, no CXL). PCIe here is non-coherent for GPU caches.
  • System-wide atomics between CPU and GPU are not natively supported.
  • Therefore unified memory works by migration — copying whole pages over PCIe on fault — not by transparent coherent access. On a Grace-Hopper system the same CUDA source has fundamentally different performance characteristics.

§14 End-to-end trace — one cudaMemcpy and one kernel launch through every component −

Tying it together: this is the complete list of hardware blocks a single vector-add touches, in order, on this exact machine.
PHASE 1 — allocate
  cudaMalloc(&d_a, N*4)
   ├─ libcudart → libcuda → ioctl to nvidia.ko
   ├─ driver picks a device VA range in the 49-bit unified space
   ├─ driver allocates physical GDDR6 pages via the GPU memory manager
   ├─ driver writes page-table entries into VRAM (via BAR1 or a copy engine)
   └─ GMMU TLBs invalidated for that range

PHASE 2 — host → device copy  (pinned source, the fast path)
  cudaMemcpyAsync(d_a, h_a, N*4, H2D, stream)
   ├─  1  driver encodes a copy method into the pushbuffer (ring buffer in memory)
   ├─  2  CPU issues ONE 4-byte MMIO write to the doorbell register in BAR0
   │        └─ crosses: core → L1/L2 → L3 → Infinity Fabric → IOD → PCIe root complex
   │           → PCIe Gen4 ×8 link → GPU Host Interface
   ├─  3  GPU PBDMA DMA-reads the pushbuffer back across PCIe
   ├─  4  Front End decodes the method; GigaThread Engine schedules the channel
   ├─  5  Copy Engine 0 issues PCIe read requests (MaxReadReq 512 B)
   │        └─ each request: AMD IOMMU translates IOVA → host PA
   │           → IOD probe filter snoops CPU caches for coherence
   │           → UMC → DDR4 row activate → data returns as 128 B TLPs
   ├─  6  data lands in GPU: Host Interface → XBAR → L2 partition → memory controller → GDDR6
   └─  7  Copy Engine writes a semaphore/fence value; optionally raises MSI-X

PHASE 3 — kernel launch
  vecAdd<<<grid, 256>>>(d_a, d_b, d_c, N)
   ├─  1  kernel params (≤4 KB) copied into the constant memory bank
   ├─  2  launch method → pushbuffer → doorbell → PBDMA → Front End   (as above)
   ├─  3  GigaThread Engine / Compute Work Distributor receives the grid
   ├─  4  CWD computes per-SM occupancy from: 256 threads/block, registers/thread,
   │        shared mem/block → against 1536 threads, 65536 regs, 100 KB, 24 blocks per SM
   ├─  5  blocks dispatched across 5 GPCs → 29 TPCs → 58 SMs, order unspecified
   ├─  6  each SM's dispatch unit allocates registers + shared memory, splits the
   │        block's 8 warps across the 4 sub-partitions (2 warps each)
   ├─  7  per warp: L0 I-cache fetch → warp scheduler eligibility → dispatch
   ├─  8  INT32 pipe computes i = blockIdx.x*blockDim.x + threadIdx.x
   ├─  9  LSU issues LDG → coalescer merges 32 addresses into 4 × 32 B sectors
   ├─ 10  µTLB → (miss) GPC MMU → hub MMU → page-table walk in VRAM
   ├─ 11  L1 data cache tag lookup → miss → XBAR → L2 → miss → GDDR6
   ├─ 12  ~500 cycles of latency, covered only by the other 11 warps per scheduler
   ├─ 13  FMA pipe: c = a + b, one warp per clock
   ├─ 14  LSU issues STG → coalesce → L1 (write-through for global) → L2 → GDDR6
   └─ 15  EXIT; SM frees the block's registers and shared memory; CWD sends the next block

PHASE 4 — device → host, and synchronise
  cudaMemcpyAsync(h_c, d_c, N*4, D2H, stream); cudaStreamSynchronize(stream)
   ├─  1  Copy Engine 1 reads GDDR6 → L2 → XBAR → Host Interface
   ├─  2  PCIe writes → IOMMU translate → IOD probe filter invalidates stale CPU lines
   │        → UMC → DDR4
   ├─  3  GPU writes the completion fence into pinned host memory
   └─  4  host either spin-polls that fence (low latency, burns a core) or blocks on
          the MSI-X interrupt (low CPU, ~µs wakeup latency)
Count the crossings. A trivial vector-add touches roughly 35 distinct hardware blocks and crosses the PCIe link four times. Two of those crossings (phase 2 and phase 4) move all the data at 14 GB/s, while phase 3 runs at 300 GB/s. For any kernel with O(1) arithmetic per element, the PCIe transfers dominate totally — which is the entire argument for keeping data resident on the device across many kernels rather than round-tripping.
